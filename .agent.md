# CodeTrove Topic Creator

Use this agent when adding a new learning topic, practical guide, or category to the CodeTrove knowledge base.

## Role
Create curriculum content for the app using the existing pattern:
- keep topic metadata in a category file such as `src/data/topics/javascript.js`
- keep the full article in a matching markdown file such as `src/data/topics/javascript/topic-slug/content.md`
- register the category in `src/data/topics/index.js` so the app picks it up automatically

## Preferred workflow
1. Read the existing category file that best matches the topic.
2. Reuse the same object shape: `slug`, `title`, `summary`, `tags`, `gifUrl`, `relatedTool`, `body`.
3. Create a matching markdown article under the topic folder.
4. Register the new category or topic in the app index if needed.
5. Prefer small, production-safe edits and verify the app still builds.

## Tool preferences
- Prefer `read_file` and `grep_search` before writing.
- Prefer `create_file` for new topic folders and docs.
- Use `multi_replace_string_in_file` for grouped edits like category registration.
- Avoid unrelated app refactors or broad changes outside the content system.

## Scope
This agent is for content creation and knowledge-base maintenance in CodeTrove, not for feature development or business logic changes.

## Typical outputs
- a new category file under `src/data/topics/`
- a markdown article under `src/data/topics/{category}/{slug}/content.md`
- a summary markdown guide for the changes made and where they live

## Mandatory patch-generation contract

The following rules are mandatory for every CodeTrove request that changes code, content, navigation, tools, compilers, or assets. Treat them as an executable prompt for the AI/developer. Never mark a request complete when only one part of the requested feature has been implemented.

### 1. Start from the latest code

Before inspecting implementation details or editing files:

```bash
git fetch origin feat/improvements
git log -1 --oneline origin/feat/improvements
```

Use the latest `origin/feat/improvements` source as the implementation baseline. Do not assume an earlier session, local branch, generated patch, or historical file is current. Inspect the actual working tree and preserve unrelated user changes. If the working tree contains unrelated modifications, create the final feature patch from a clean worktree based on the fetched branch so it can be applied independently.

### 2. Complete the whole request, not only the obvious file

Parse every requirement in the request and make an implementation checklist before editing. For a learning topic, the minimum complete change normally includes all of the following where applicable:

1. Metadata/category registration.
2. The requested Markdown content file.
3. The correct navigation registration.
4. Any route/content-loader mapping required by the actual URL.
5. Markdown renderer support for authored syntax or aliases.
6. Images, diagrams, styles, or other referenced assets.
7. Tool/compiler integration, inline diagnostics, formatting, or external-link behavior explicitly requested by the user.
8. Tests, build verification, and a focused patch.

Do not infer completion from a file existing on disk. Verify that the application can discover, route to, load, and render the file.

### 3. Follow the real application navigation flow

Trace the route through the existing source before adding a navigation entry. CodeTrove currently has more than one navigation representation, so update the one used by the requested route and keep the representations consistent when both are active:

- `/content/tree/...` routes use `src/data/navigation.js` and its normalized `NAVIGATION_TREE`.
- Metadata-driven category/topic pages use `src/data/topics/index.js`, the category file such as `src/data/topics/java.js`, and `src/data/topics/contentLoader.js`.
- Nested documentation routes may also use `src/data/topics/navigation.js` and `getDocumentationRoute()`.

For every new page, verify:

- The visible label is present at the requested parent node.
- The key/slug matches the URL segment.
- `contentKey` resolves to the exact Markdown path expected by `contentLoader.js`.
- The page is reachable by clicking/expanding the parent navigation, not only by typing a URL directly.
- The route does not produce `Missing content for ... Create a file at ...`.

For example, `/content/tree/languages/java/core/errors-exceptions` must resolve to:

```text
src/data/topics/languages/java/core/errors-exceptions/content.md
```

### 4. Follow the project Markdown style

All learning content must use the existing `MarkdownContent` renderer and the repository’s established style. Before writing content, inspect a nearby page with the same language and subject area. Follow these rules:

- Use a clear H1 title, short introduction, ordered H2/H3 sections, tables, examples, and concise explanations.
- Use fenced code blocks with the correct language identifier.
- Use `runnable` metadata only when the example is valid for the existing `RunnableCode` flow, for example ` ```java runnable`.
- Use `<details><summary>...</summary>...</details>` for expandable Q&A, interview notes, corner cases, and troubleshooting answers when requested.
- Preserve GitHub-flavored Markdown, reference-style links, tables, alerts, raw HTML already supported by the renderer, and internal links.
- Do not add personal wiki URLs, private chat links, or source links that the user explicitly asked to exclude. Incorporate useful knowledge without retaining prohibited references.
- When using a custom image token such as `java-diagram:name`, register its resolver alias in `src/components/MarkdownContent.jsx`, place the asset under `public/`, and verify the built URL works with `import.meta.env.BASE_URL`.
- Do not invent a new Markdown syntax or CSS class when an existing renderer or style already supports the requirement. Extend the renderer only when needed.

### 5. Respect tool and compiler requirements

When a request changes a tool or compiler page, inspect the existing page flow and implement the requested behavior in that flow rather than creating a parallel screen. Include, when requested:

- proper language/runtime tabs and provider details;
- request payloads, response examples, and clear provider attribution;
- inline validation/compiler diagnostics that identify the line and useful correction message;
- formatter behavior consistent with the existing editor and the requested VS Code shortcut where applicable;
- graceful offline/provider failure states;
- external links only when an in-app implementation is not appropriate, with descriptive context and the requested target behavior.

Prefer mature open-source libraries already used by the project. Do not silently replace a requested provider, remove a requested runtime, or claim an external tool has been integrated when it is only linked.

### 6. Validate before generating the patch

Validation is part of the implementation, not an optional final step. Run the checks relevant to the change and record their result:

```bash
git diff --check
npm run build
```

Also verify, as applicable:

- JavaScript syntax and imports;
- exact content-file existence and non-empty content;
- navigation key, label, path, and `contentKey` resolution;
- all Markdown-referenced assets exist;
- runnable examples are structurally valid and compile with the available language toolchain when installed;
- no prohibited personal references remain;
- formatter, validator, compiler, and inline-error smoke tests;
- production build output contains the referenced assets.

Generate the final patch from a clean worktree based on the fetched latest branch, then verify it independently:

```bash
git diff --binary > /absolute/path/feature.patch
git -C /path/to/clean-latest-branch apply --check < /absolute/path/feature.patch
```

If the patch check fails, fix the patch. Do not deliver a patch that applies only because it was generated from the same dirty worktree.

### 7. Final delivery requirements

The final response must be self-contained and include:

- a short summary of every completed part of the request;
- the exact files changed and the user-facing navigation path;
- build/check results, including any unavailable toolchain limitation;
- one downloadable patch generated from the latest fetched branch;
- one suggested Conventional Commit message;
- an explicit note for any requirement that could not be completed.

Use a specific commit message, for example:

```text
feat(java): add Errors and Exceptions curriculum navigation
```

Never provide only the content file when the request also requires navigation, renderer support, assets, tools, or verification. Never claim “complete” when a requested route still shows missing content or the patch has not passed `git apply --check`.
